- **What it is.** A fork branch of MaxPane that adds one dashboard, PEPEPANE, behind a lean `pepepane` entrypoint installed on the worker host (VPS seat #7 first, Mac seat #420 as parity). Two processes on the VPS: the TUI as a new unprivileged user `imd-dash`, and a ~700-line stdlib root broker `imd-dashd` behind a unix socket that owns every write verb (plan → apply → verify, audited) and every read inside the 0700 worker home.

- **Decided by the owner on 2026-09-26.** The branch and the console script are both named `pepepane`. The branch may issue control actions through the broker (§16 #1); MaxPane `main` stays read-only. Every other §16 item was decided the same day: each takes its recommended default, and #7 is yes.

## 1. Purpose, scope, success criteria

**Who.** One operator (the owner) running one IdentityMD seat per machine: seat #7 (Codex CLI 0.157.0, systemd unit `imd-worker.service`, user `imd-worker`, `/opt/imd-worker`, IONOS VPS `imd-vps`, no Docker) is the primary target; seat #420 (Claude Code 2.1.282, Docker container `imd-worker` on the Mac) is the parity target (vps §1; safety §1).

**What.** A branch of MaxPane (`/Library/Vibes/autopull`, Textual TUI) that adds exactly one dashboard, PEPEPANE, behind a lean console script `pepepane`, installed **on the worker host**, that (a) shows the seat's live state, work ledger, cost, configuration, machine and standing in real time from **local** sources, using `api.imd.fun` only where nothing local exists, and (b) offers a **control panel** of a fixed, audited verb set (restart, drained restart, stop/start, boot enable, skills toggle, orphan kill, doctor) through a privileged broker. Tier changes, capacity changes and updates are **not verbs in v1** — the CONTROL modal prints one static line per procedure pointing at the runbook, and each becomes a real verb only after the owner has exercised the procedure by hand (§11, §16 #3).

**Starting point.** SURFBOARD's `a` AGENT view (`screens/surf.py:2366`, hero + cards + RECORD; maxpane §1) lends its vocabulary and rules — six hero boxes, meaning-bound colours, `as of HH:MM` per panel, honest number shortening, a `»` detail modal — but not its widgets, which render `/seats`/`/contributors`/`/workers` envelopes (maxpane §2).

**Done when (success criteria, each testable):**

1. On the VPS, `ssh -t imd-dash@imd-vps pepepane` renders the PEPEPANE screen within one poll interval with every local panel populated while `--offline` is set (**no API read by the TUI**, and the broker skips its own standing read because every plan request carries `offline: true` — §4.3, §11), and the API-fed cells read `local only` (§6, §8).
2. The hero answers in one glance: alive?, doing what?, how did today go?, verdicts?, safe to touch?, will it survive a reboot/OOM? (§8 hero).
3. The ledger reproduces, for the 40+40 reconciled attempts of fill3, the control plane's `turns`/`inputTokens`/`outputTokens`/`cachedInputTokens` exactly (fill3 §2–§3), and joins verdicts by `submissionHash[:12]` (fill6 §3).
4. A restart issued from the TUI is refused while a task runs. `apply` performs a **fresh** standing read and a **fresh** journal scan at apply time, requires ≥4 idle heartbeats, `standing.running == []` from that read (or a typed `local-only` ack), a newest anchored lifecycle line that is terminal (no open `accepted` row), `outbox == 0` and an active unit — the last two fail closed when unreadable — then execs `systemctl` immediately; `verify <plan_id>` reports `shutting down → runtimes:` within 30 s as `verified`, `admitted` separately as `connected`, and the audit holds one line per phase with journal cursors before/after (§11).
5. No process that renders UI ever opens `config.json`, `auth.json`, `tools.env` or `.credentials.json`; the projection canary (key-name, value-pattern, **hex64-vs-whoami** and **exact-8-keys** checks) and the install-day negative checks pass (§13, §14).
6. The cold footprint of the `pepepane` entrypoint is measured (CI assertion ≤160 MiB on the Mac; VPS `memory.peak` recorded at install) and fits the `MemoryMax=256M` slice (§12).
7. `git merge main` from upstream MaxPane conflicts at most in `pyproject.toml` (§15) — the seat stylesheet lives only in `SeatScreen.DEFAULT_CSS`, nothing is appended to `themes/minimal.tcss`.

**Out of scope for v1** (§17): any web/WebSocket UI, chain reputation rows, notifications, editing task-hint files, workspace pruning, tier/capacity/update as verbs (plan-only text, not enum entries), a seat registered in the shared `maxpane` menu, any dollar figure (including Claude Code's list-price estimate).

## 2. The brief against the measured reality

**"Websocket connections" — there is no local endpoint.** The daemon opens no port, unix socket, status file, metrics endpoint or event log; its only connection is an outbound WSS to `api.imd.fun` whose frames are Ed25519-signed by the device key (bundle §3, §4; vps §5 `ss -ltnup`: sshd, resolved, chrony only; contradictions #17). The CLI has no `--json` on any command — `imd status --json` prints the plain text (bundle §1; fill4 §8). `imd doctor` spends a runtime turn and leaves a `work/doctor-*` transcript (fill3 §0; fill6 §4), so it is a manual verb, not a source. Subscribing to the daemon's WSS as an observer would need the device key — never (bundle §4).

**What "local" therefore means** (bundle §8; collectors §1; vps §2):

| Local source | VPS (#7) | Mac (#420) |
|---|---|---|
| Daemon stdout/stderr | journald `imd-worker.service` (`user-1000.journal`, SplitMode=uid) | Docker json-file via `docker logs` |
| Config-home names/mtimes | `/home/imd-worker/.identitymd/{outbox,work}` (0700, UMask 0077) | volume `imd-home` via `docker exec` |
| Runtime transcripts | `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl[.zst]` | `/home/imd/.claude/projects/<slug>/*.jsonl` via `docker exec` |
| CLI text | `imd status\|skills\|tools\|whoami` (as imd-worker) | `docker exec imd-worker imd …` (**container-reported**, §4.2) |
| Unit/host | `systemctl show`, cgroup files, `/proc`, `sar` | `docker inspect`, `docker stats` |

**Where the API is unavoidable and why.** Verdicts (accepted/rejected/failed/pending) and failure reasons never appear locally: a locally failed run prints the same `submitted … for <node8>` + `submission stored (<hash12>) — awaiting verdict` lines as a success (fill6 §1; fill1 §4: journal 23:37:56.013Z ↔ plane `failed runtime_error` 23:37:56.035Z). The daemon persists no run history (fill6 §4). Only `/seats/<id>/standing` (running now, breaker, `recentFailures[].reason` for 24 h), `/seats/<id>?work=N` (verdict per `submissionHash`), `/jobs/<jobId>/submissions` (per-attempt `outcome`, `failureReason`, `failureClass`, no time window — fill1 §4; cost §4) and `/health`+`/services` (fleet, verifier) carry that information (fill5 §1, §4, §7). **Failure reasons exist only remotely: on the standing route for the last 24 h, or on `/jobs/<jobId>/submissions` for any attempt whose `jobId` is known** (fill1 CONSTRAINTS). So "API at most a fallback" is honoured literally for everything except one column — verdicts and their reasons — where it is the **sole** source and is labelled `api · as of HH:MM`.

**Three outcome axes, never summed** (collectors §4; cost §3; fill5 §3): (1) control-plane attempts on `/seats/<id>` (= `work[]` rows; `attempts = accepted+rejected+failed+pending`, 417/417 seats) and `/contributors` (per **device**, no `failed` column, `pending = attempts − accepted − rejected` on 448/448 rows, exceeds `/seats` by research answers + lease-closed submissions); (2) chain ERC-8004 feedback rows (batcher backlog of 837 queued batches, 20 h with no row — fill4 §2); (3) standing/doctor failed runs (24 h window, with reasons). PEPEPANE shows axis 1 by hash join and axis 3 as reasons; axis 2 is out of scope (§17).

**Other realities the brief did not price:** config changes need a daemon restart (no reload path, no pause/drain verb — safety §1; contradictions #13); the device private key sits in the same 0600 file as every operator setting (safety §1); tasks run as the worker uid with filesystem-root read and loopback reach (vps §2; safety §4); the VPS journal cap is ≈347 MiB, not 4 GiB (fill8 §2); releases ship **3–6 per day** (15 tagged releases 2026-09-21…24, bursts 1–2 h apart — bundle §6, bundle CONSTRAINTS, safety §2) so every text parser is a drift risk; the aidude mode-B writer over-counts cost ~2× and has no local systemd mode (fill4; contradictions #5).

## 3. Approaches considered and the recommendation

**A. ops-minimal (winner, 3/3 judges; 159.5 points).** Two processes on the VPS: the TUI as a new uid `imd-dash` (group `systemd-journal`) reading journal/unit/cgroup/API itself, plus a socket-activated root broker `imd-dashd` (stdlib Python on `/usr/bin/python3`, fixed verb enum, `SO_PEERCRED`, plan→apply 60 s, audit) that drops to `imd-worker` for home reads and stays root only for `systemctl`/`kill`. Realtime = `journalctl -f -o json` in a manager-owned thread drained into the ordinary RefreshGuard tick. Ledger = sqlite keyed `(seat, node8, acceptedAt)` + `hash12`. API only for verdicts/standing/plane. Nothing registered in the `maxpane` shell (lean entrypoint). Nine verbs, six apply in v1. Trade-offs: thinner operator surface (no queue line, no auth-degraded rule, no TODAY box, no drain), a few internal slips (audit readability, `configChangedSinceStart`, broker MemoryMax, one size figure) — all fixed here.

**B. operator-experience (134.5).** Best operator insight: TODAY/VERDICTS/TOKENS hero, NOW queue line, composite "runtime auth degraded" rule, COST buckets with turn-1 context/wall/TTFT, drain-restart, `--offline`, event-driven API cadence, task-hints fingerprint. Trade-offs that lost: registers at key 9 *and* ships a lean entrypoint (six surfaces + four `MANAGER_ATTRS` copies for a Mac convenience); an always-on tmux TUI service (permanent ~142 MiB resident, `PrivateTmp` hides the tmux socket from `tmux attach`); `NoNewPrivileges=no` on the root broker on a wrong premise; broker on the venv interpreter; `hints-put`, `tier` and `capacity` apply in v1; polls `standing?queue=0` yet renders the queue line (that request returns `queue: null`, fill5 §1); hero red on a single `disconnected` beat — measured **5–11 `disconnected` beats per day** on the VPS (5 in the last 24 h, 80 in 7 days; fill5 §2, vps §3) and 35 on the Mac since 09-20 (fill1 FACTS), with six control-plane redeploys in nine hours (fill5 §7), so a single-beat rule flashes red several times a day for events that are not the seat's fault.

**C. security-least-privilege (122).** Clearest trust-zone write-up, GATE hero box, inverse verb in every plan, post-apply verify on `admitted`, projection canary, sshd `Match User`, install-day negative checks, extra unit hardening. Trade-offs that lost: `IPAddressDeny=any` + `RestrictAddressFamilies=AF_UNIX` on the very unit whose children run `imd status`/`imd skills`/`imd doctor` (network calls: `GET /enrollments`, `GET /skills` — bundle §1; collectors §1.2) so its own read verbs fail; `workspace.prune`, `work.read`, `hints.apply`, `tier.set` apply in v1 against fill8 CONSTRAINTS and safety §7; writes disabled whenever standing is >120 s stale (no restart during a redeploy wave); no durable row ledger; registers at key 9.

**Recommendation: A, with these grafts** (all recorded as decisions in §15): from B — NOW queue line, drain-restart, auth-degraded rule, COST percentiles (turn-1 context, wall p50/p90, TTFT), `startedAtUtc`+`completedAtUtc`, hints fingerprint (read-only), manager-side tail drain, `gracefulStopPossible`, `--offline`, event-driven API re-reads, divergence footer; from C — GATE hero box, `inverse` + post-verify in every plan, `outbox == 0` in the gate, `audit-tail` verb, projection canary audit, sshd `Match User imd-dash`, `RemoveOnStop`/`PrivateDevices`/`ProtectKernelTunables`/`RestrictNamespaces`/`ProtectControlGroups`/`LogsDirectory` on the broker, sha256 `MANIFEST`, install-day negative checks. Rejected from both: `IPAddressDeny=any` on the broker, always-on tmux service, key-9 registration, hints-put, prune, tier/capacity apply, single-beat red. **Added by review (Appendix C):** runtime-executing children run as their own transient units with the worker's sandbox posture rather than inside the broker's cgroup; `apply` returns immediately and verification is a separate read verb; the gate is re-read fresh at apply; the canary is value-aware for 64-hex; the redactor strips control characters first.

**4.1a Child environment (verbatim, both child kinds).** `HOME=/home/imd-worker`, `PATH=/opt/imd-worker/bin:/opt/imd-worker/node/bin:/usr/local/bin:/usr/bin:/bin`, `NO_COLOR=1`, `LANG=C.UTF-8` — and nothing else; `cwd=/tmp`. `node` is not on root's PATH (`node --version` fails as root — vps §1), and `runuser -u imd-worker` from root needs exactly this PATH plus `cd /tmp` or `imd` dies with `env: 'node': No such file` (fill2 CONSTRAINTS). The unit's own env is `HOME` + the same `PATH` (vps §1). The `FakeBroker` argv recorder test asserts this env dict byte-for-byte.

**4.1b Transient-unit children (`imd_dashd/child_unit.py`).** Every child that executes `imd` (`whoami`, `status`, `skills`, `tools`, `doctor`, `skills add|remove`) or parses hostile-size files (the `sessions` summariser, §5.4) runs as its **own transient service** so that (1) a model-driven runtime process never runs inside the root broker's mount/network/cgroup context with *more* reach than the daemon's own runs get, and (2) an OOM or hang in the child lands in the child's cgroup, never in the broker's (the broker may be holding an armed drain). Mechanism: `systemd-run --uid=imd-worker --gid=imd-worker --wait --collect --pipe --quiet --unit=imd-dash-<verb>-<seq> --working-directory=/tmp --setenv=HOME=… --setenv=PATH=… --setenv=NO_COLOR=1 --setenv=LANG=C.UTF-8 -p NoNewPrivileges=yes -p UMask=0077 -p PrivateTmp=yes -p ProtectSystem=strict -p ProtectHome=tmpfs -p BindPaths=/home/imd-worker -p TemporaryFileSystem=/opt:ro -p BindReadOnlyPaths=/opt/imd-worker -p InaccessiblePaths=/run/dbus -p InaccessiblePaths=/run/systemd/private -p InaccessiblePaths=/run/imd-dash -p InaccessiblePaths=/home/imd-dash -p InaccessiblePaths=/var/log/imd-dash -p IPAddressDeny=<value of systemctl show imd-worker.service -p IPAddressDeny, read at broker start> -p MemoryMax=512M -p TasksMax=64 -p RuntimeMaxSec=<per verb, §11> -- <argv>`. The posture is the worker unit's own (vps §1; safety §1) — including the `IPAddressDeny` list that keeps tasks off cloud metadata, RFC1918 and the operator's other hosts — copied at broker start so the two cannot drift silently; if the read fails the broker refuses runtime-executing verbs with `error: child_posture_unavailable` rather than running them unfenced. `RuntimeMaxSec` makes systemd SIGTERM then SIGKILL the child's **whole cgroup** — the process-group kill a manual probe lacked when it hung 35 h (vps §6.1); the broker's `subprocess.run(timeout=RuntimeMaxSec + 15)` is the belt, and on that timeout it runs `systemctl kill --signal=KILL imd-dash-<verb>-<seq>.service`. Unit names are `imd-dash-*`, so the orphan finder (§11) excludes them by cgroup. The broker's own hardening (`RestrictNamespaces`, `PrivateDevices`, `ProtectSystem=strict`, §12.1) therefore never applies to a runtime child — it applies only to the stdlib broker process and its in-process stdlib children. **Unmeasured until the install-day probe:** `imd status` and `imd doctor` completing under exactly this posture, with the child scope's `memory.peak` recorded (§14). The gate's standing read stays an in-process `urllib` child (no runtime, only `api.imd.fun`).

**Trust boundaries.** (1) Tasks run as `imd-worker` with filesystem-root READ (Codex `permission_profile`, vps §2) — everything under `/home/imd-dash`, `/run/imd-dash`, `/var/log/imd-dash` and `/opt/imd-dash` is invisible to them (`ProtectHome=tmpfs`, `TemporaryFileSystem=/opt:ro`, plus the drop-in). (2) Loopback cannot be denied to the worker (DNS stub at 127.0.0.53; safety §4) — therefore **no TCP listener anywhere**; the only IPC is a unix socket gated by uid via `SO_PEERCRED`, not by path. (3) Root code = the broker only, stdlib only, ~700 lines, so a Textual/pydantic/httpx bug cannot run as root; the broker's only network use is the gate's `urllib` standing read (dropped child) and the transient-unit `imd` children, which run under the worker's posture, not the broker's. (4) The device private key is read by nobody but the projection script, which runs as `imd-worker` and emits an allowlist; the raw file never crosses the socket, and the canary is value-aware for the one secret whose byte shape equals a public field (§13). (5) The TUI holds no secrets and writes only `~/.maxpane`.

## 9. Realtime path

**Follower.** `SeatManager.start_tail()` starts one `threading.Thread(daemon=True)` running the follower subprocess: VPS `journalctl -u imd-worker.service -o json -f --after-cursor=<cursor>` (first run `--since -14d`); Mac `docker logs -f --tail 200 --timestamps imd-worker` after a one-shot, **untrusted** `docker logs --since <watermark>` backfill (25 s timeout; discarded whole when its newest stamp is older than the watermark — §5.1). Each line → `redact()` (control-character strip first) → `classify()` (anchored grammar, Appendix B) → `LogLine(ts, invocation, text, kind, cursor)` → `queue.Queue`. The thread stamps `aliveAt` every second even when no lines arrive; on subprocess exit it restarts with backoff 1→30 s and reports `tail: exited rc=N — retry in Ns` through `sources.tail.reason`. **Call site:** `seat_cli.py` after constructing the manager, and only when not `--once`; never `fetch_and_compute()`, never the screen (§4.3). Stopped in `close()`.

**Drain.** `SeatManager.fetch_and_compute()` (on the ordinary RefreshGuard tick, `--poll-interval 5`, MaxPane's minimum) calls `drain()` first: pure ingest → sqlite upsert → ring → detector state; then the tiers. `SeatLog.update_data(seat_log_lines=<new since seq>, seat_log_seq=…)` appends only unseen lines (the `RichLogFeed` batch-per-poll contract); every other widget replaces. Coalescing: a 48 k-line backfill is one drain, one refresh. Latency ≤5 s after the daemon prints; the daemon itself throttles phase lines to 15 s and heartbeats to 30 s, so nothing is lost by not pushing. No Textual import in `data/`; no `post_message`/`call_from_thread` (MaxPane has no precedent for either — maxpane §4). Decision recorded: "tail subprocess in `data/seat_tail.py` allowed; drained on the poll tick, not a screen timer".

**Watermarks.** VPS: `__CURSOR` → `~/.maxpane/seat_tail.json` `{"kind":"journald","cursor":"…","lastTsUtc":"…","invocation":"…"}` after each drained batch; a first entry newer than `lastTsUtc + 60 s` **or** a non-zero exit → `--since <lastTsUtc>` + gap footer (§5.1). Mac: newest daemon ISO stamp ingested, dedup `(ts, text)`. Restart boundary = the `runtimes:` startup line (resets `submittedSinceStart`; VPS `_SYSTEMD_INVOCATION_ID` corroborates). Sessions watermark = newest rollout/transcript mtime handed to `sessions --since`. Ledger rows are idempotent upserts (mutation test: replaying 500 lines twice → identical row count).

**Staleness constants** (named, with `#:` blocks, clock injected — plan R4 shape): `HEARTBEAT_STALE_S = 90` (amber; 3 missed beats), `HEARTBEAT_DEAD_S = 300` (red `offline` only together with `standing.presence.connected == false` or 2 consecutive `disconnected` beats); stale heartbeat but `presence.connected == true` and `heartbeatAgeMs < 60 000` → `plane sees us · local tail stale` (a tail problem, not a seat problem); `TAIL_DEAD_S = 45` without a thread `aliveAt` → `sources.tail.ok = false`, hero red; `standing`/`seatWork`/`reasons`/`plane` → `unavailable (reason)` after 3 consecutive failures or 10 min without a good read; every panel's `as of` comes from its own source's `asOfUtc`, never the fold time. The idle-beat counter counts only heartbeats newer than `now − 3 min`, so a frozen tail cannot vouch "idle".

**Docker equivalent.** Same thread and queue; `docker logs -f` exits at every container restart (expected, rc 1) — the backoff path re-attaches with the trusted `-f --tail 200` form and runs the `--since` backfill under the discard rule; `--since` is never the follower. Liveness comes from the follower and heartbeat age, never from `docker inspect` (which may wedge); an inspect timeout turns UNIT amber and never the hero (fill4 §1).

## 11. Control panel

**Charter break, recorded.** MaxPane is strictly read-only (autopull CLAUDE.md constraint 1; seat PRD §7 — lineage §2). `docs/decisions.md` entry: "PEPEPANE-CTRL 2026-09-26: the `pepepane` branch may issue a fixed set of local control verbs through a privileged broker with plan→apply and an audit log; the TUI process itself remains read-only; MaxPane `main` stays strictly read-only." **Approved by the owner on 2026-09-26** (§16 #1). Precedents: `bin/send.sh` plan block + `--yes`, burnkeeper arming (safety §3).

**Protocol** (both runtimes; VPS over the unix socket, Mac in-process): request one JSON line `{"v":1,"verb":"<enum>","args":{…}}`, response one line `{"ok":bool,"data"|"plan"|"result"|"error":…}`. Fixed enum, typed args, no shell, fixed argv, per-verb hard timeout, whole-cgroup kill on timeout (§4.1b). Write verbs are two-phase and **race-free by construction**:

- **Plan ids are single-use.** `plan` returns a random 16-hex `plan_id` valid 60 s; `apply` consumes it atomically under a **broker-wide write lock** — a second `apply` of the same id → `error: plan_spent`, a late one → `error: plan_expired`.
- **At most one write verb in flight per broker.** While a `systemctl …`, an `imd skills …`, a `doctor` or a drain fire is executing, any other `plan`/`apply` of a write verb → `error: busy` naming the in-flight `{verb, plan_id, since}` (also surfaced as `control.inFlight` and in the CONTROL modal). Two TUIs, or a TUI and a scripted `pepepane --once`, therefore cannot double-restart.
- **`apply` returns as soon as the command exits** — `{"ok":true,"result":{"outcome":"applied","exit_code":0,"cursor_before":"…","audit_seq":1287}}` — so no request outlives the 20 s client timeout (a `systemctl restart` takes 0.3 s — fill1 §1; `admitted` can lag past a minute during a redeploy wave — fill5 §7, reconnect backoff ceiling 30 s — bundle §4). The operator would otherwise see a client timeout on a *successful* restart, re-plan and re-apply, and land a second restart on a daemon that may have just accepted work — the exact double restart the two-phase design exists to prevent.
- **Verification is a separate read verb.** `verify <plan_id>` → `{"verified": true|false|null, "connected": true|"pending"|null, "verify_lines": […], "cursor_after": "…", "elapsed_s": 4.1}` polled by the TUI on the ordinary RefreshGuard tick until `verified` is not `null` (the broker keeps the plan's post-apply journal watch for 120 s). **Restart success and reconnection are two facts and never share one verdict**: `verified = true` when `shutting down` is followed by `runtimes:` within 30 s (that pair is +0.3 s on 8/8 historical restarts — fill1 §1); `connected` is `true` once `admitted (session …)` appears and `pending (reconnecting since HH:MM)` until then — during a redeploy wave `admitted` can lag past 60 s (225 `reconnecting`, 70 `server_shutdown`, 63 HTTP 502 in 4 days — vps §3.3), and that must not read as a failed restart or nudge the operator toward `--force`. LIVE owns `connected` afterwards. Same split for `start` (`runtimes:` = verified; `admitted` = connected) and `stop` (`shutting down` + `ActiveState=inactive` = verified).
- **Per-verb client timeouts** (TUI side): every read verb 20 s; `plan` 20 s (it includes one fresh standing read, 0.1–1.2 s measured); `apply` 20 s (commands exit in ≤ 2 s; the transient-unit verbs `skills set` and `doctor` are the exceptions and return `outcome: started` immediately, their completion arriving via `verify`); `verify` 20 s.

Every plan, apply, verify and refusal appends an audit line.

**Idle gate G** (for `restart`, `stop`, `drain-restart` apply). The plan shows a preview; **`apply` re-reads everything fresh** — cached preconditions are not a gate. Both halves a cached gate would consult are cadence signals with a ~30 s blind window at exactly the cadence tasks arrive: the heartbeat's `N task(s) running` is a 30 s local timer (`LIVENESS_MS`, bundle §3.1), oracle tasks are 22–40 s long and a busy seat cycles every ~40 s (fill5 §1; safety §0), so "4 idle beats + a 25-s-old `running: []` + a task accepted 15 s ago" is a normal state, not an edge case. At apply the broker:

1. **(a) idle beats** — scans the journal (root) / the tail (Mac) for ≥ `IDLE_BEATS_REQUIRED = 4` consecutive `· idle ·` heartbeats among heartbeats newer than `now − 3 min` (≈2 min of idleness);
2. **(b) plane** — performs a **new** `GET /seats/<id>/standing` read (in-process `urllib` child as `imd-worker`, 8 s timeout, retry once; returns only `{running_count, at}` to root) and requires `running == []` **from that read** (`standing_age_s ≤ 2`); if the read fails, or the request carries `"offline": true` (which every plan request carries when the TUI runs `--offline`), the gate is `local-only` and apply requires the typed `local-only` ack (a redeploy wave must not block a 3 a.m. restart — fill5 §7);
3. **(c) lifecycle** — scans the journal for the **newest anchored lifecycle line** and requires it to be terminal: `submitted`/`answered`/fuzz outcome/`submission stored`/`cancelled`… — i.e. no `accepted <role> <node8>` without a later terminal line. This is the freshest local signal that exists (fill6 §1 grammar), it is read by the broker itself (never trusted from the TUI's ledger), and it closes the heartbeat blind window down to the assign→accepted lead;
4. **(d) outbox** — `ls outbox/` as `imd-worker` must return 0 files. **Fail closed:** a timeout or unreadable directory → `error: gate_unknown(outbox)`, and no typed ack can override it. A pending unacked result relies on cross-restart outbox recovery, which has **never executed** on either seat (fill1 §4: in-process re-send worked twice; `recoverOutbox` after a restart never fired) — the honest reason is "untested", not "destroyed"; wait for the ack instead;
5. **(e) unit** — `ActiveState=active` (restart) / container `Running` (Mac). **Fail closed:** `docker inspect` timed out in 2 of 3 writer cycles on 09-26 and `docker exec`/`ps` hung on 09-20 (fill4 §1; lineage §4) — unknown is `error: gate_unknown(unit)`, never "no blocker";
6. then execs `systemctl` **immediately**, and records `idle_beats`, `standing_age_s`, `plane.mode`, `last_lifecycle_line`, `outbox_files`, `unit_active` in the apply audit line's `preconditions`.

The **residual window** is the 1–4 s by which `standing.running[0].since` leads the daemon's `accepted` line (fill5 §1) plus the broker's own scan time — ~1–5 s — and the plan warning says so honestly. `--force` bypasses (a)–(c) only (never (d)/(e)), requires typing the running node8 at plan **and** apply, is **disabled when `gracefulStopPossible == false`** (Mac today), and every plan carries the warning: "a task assigned in the ~1–5 s between the gate's reads and `systemctl` may be reported as a failed run; 3 consecutive failed runs pause the seat 15 min (`breaker {failures 3, cooldownMs 900000}`); never measured — 16/16 historical restarts were idle" (fill1 §0, §6). The same six steps run inside the in-process Mac broker (tail instead of journal; `docker exec imd-worker ls outbox` for (d); `docker inspect` for (e)) and at **drain-restart's fire condition**.

## 13. Secrets and hostile-input hygiene

**Never opened, copied, displayed, cached or logged** (safety §5): `~/.identitymd/config.json` (only the broker's allowlist projection, as `imd-worker`; never its `.bak-*` copies either), `~/.identitymd/tools.env`, `~/.codex/auth.json`, `~/.codex/config.toml`, `~/.claude/.credentials.json`, `~/.claude/history.jsonl`, any `.env`, ssh keys, volume backups (`imd-home-*.tgz`), `attachment.credential_org.organizationUuid` in transcripts; the credential files' **mtimes** only (`auth-mtime`). Transcripts are summarised to metadata (model, turns, tokens, timestamps, error status); tool results and prompts never leave the summariser (safety §5.4).

**Identifiers:** device public key and wallet truncated to 8 chars in the TUI (`imd whoami`/`worker-page` convention); job/node ids full (they are the ledger's join keys); hashes shown as `hash12`.

**Redactor** (`analytics/seat_redact.py`, and its byte-identical copy `imd_dashd/redact.py` bound by an equality test; applied before render, before every sqlite/audit write and before any fixture is committed; safety §5.3; mutation-tested with the real `sk-svcac********` fragment from the 09-25 heartbeat). **Step 0 — control characters, before anything else:** strip `[\x00-\x08\x0b-\x1f\x7f-\x9f]` (C0 except `\t`/`\n`, DEL, C1) and the Unicode bidi/format controls `[​-‏‪-‮⁦-⁩]`, replacing each run with nothing (`\x1b` alone is rendered as `␛` so an attempted escape stays visible as a glyph), and apply this to every journal `MESSAGE`, API string, transcript summary string, `imd` CLI output line, orphan cmdline and audit `verify_lines`. Why it must be a dedicated step and not left to the existing layers: `markup_safety.flatten()` is `" ".join(str(value).split())` (autopull `widgets/markup_safety.py:97-115`) and drops only whitespace, so `\x1b`, `\x00-\x08`, `\x0e-\x1a`, `\x7f` and U+202E survive `sanitize_cell`; Rich `Text` strips only `[7, 8, 11, 12, 13]` (`rich.control.STRIP_CONTROL_CODES`, verified in the autopull venv: `Text('a\x1b]0;evil\x07b\x1bc\x7fd‮e').plain` keeps `\x1b`, `\x1b`, `\x7f`, U+202E); Textual writes segment text raw into the ANSI stream (`textual/strip.py`). The daemon's own sanitiser is `\s+`→space + `slice(160)` (fill6 FACTS; bundle §3.1), so a task agent's `working:` sentence carrying `\x1b]52;c;…\x07` (OSC 52 clipboard write) or an OSC title/hyperlink sequence reaches journald, the `-o json` MESSAGE, the LOG/NOW panels and the operator's terminal over ssh; the API is measured to emit raw control characters inside JSON strings (fill1 FACTS), and `working:` prose is measured model output that already forges event-like text (fill6 §2, journal line 4876). That is a network-chosen-agent → operator-terminal escape-injection channel, closed here. Textual's `Content` does call `strip_control_codes`, but this spec mandates pre-built `Text` for `Static` (below), so the redactor cannot rely on it. Then, in order:
```
sk-[A-Za-z0-9*_-]{4,}            → sk-[redacted]        (OpenAI-style, incl. server-masked fragments)
sk-ant-[A-Za-z0-9*_-]{4,}        → sk-ant-[redacted]
eyJ[A-Za-z0-9_-]{10,}\.[A-Za-z0-9_-]{10,}(\.[A-Za-z0-9_-]+)?  → [jwt]
Bearer\s+[A-Za-z0-9._~+/=-]{8,}  → Bearer [redacted]
gh[pousr]_[A-Za-z0-9]{20,}       → [github-token]
([?&](token|key|sig|signature|secret)=)[^&\s]+   → \1[redacted]
\b[0-9a-f]{64}\b                 → <hex64> unless the field is a known hash/public-key field (submissionHash, txHash, deviceKey — and deviceKey only after the whoami match of the projection canary below)
```
plus whitespace collapse and a 160-char cap on agent sentences (the daemon already applies both; bundle §3.1). Mutation proof (23): a fixture line `…working: \x1b]52;c;AAAA\x07\x1b]0;x\x07` rendered through NOW's and LOG's `render_strips()` must contain no byte < 0x20 other than the compositor's own SGR — `test_control_codes_never_reach_a_strip`.

**Markup safety.** Every third-party string (heartbeat `working:` prose, eligibility text, model ids, skill ids, failure reasons, objectives, orphan cmdlines, `imd status` output, API strings) → `redact()` (step 0 first) → `widgets/markup_safety.sanitize_cell`/`safe_markup`; `Static` gets a pre-built `Text`; a `DataTable.add_row` `MarkupError` would kill the app later in `_on_idle` (rules/widgets.md via lineage §3).

**Projection canary — value-aware.** The one secret this design exists to protect is a 64-hex Ed25519 private key that is byte-shape-identical to the allowed public `deviceKey` (both 64 hex — bundle §2; safety §1 FACTS), so neither `sk-…` nor `eyJ…` can ever match it and a key-name check catches only the case where the projection dumps the field under its own name. The broker therefore refuses the `seat` projection (`error: projection_refused`, audit `canary: <kind>`, the TUI shows CONFIG as `config projection unavailable — broker refused payload (canary)` in red) when: (1) any key matches `/privateKey|devicePrivateKey|mnemonic|secret/i`; (2) any value matches `sk-…`/`eyJ…`; (3) the `deviceKey` value ≠ the public key `imd whoami` printed (`canary: devicekey_mismatch` — the audit line carries the plan/seq only, never either key); (4) any **other** 64-hex value appears anywhere in the output; (5) `projection.py` itself reports the source object does not have exactly the 8 known keys (`server, deviceKey, devicePrivateKey, maxConcurrency, wallet, tokenId, skillsOptOut, inference`) — a renamed or added key in a future build fails closed (formats already changed between builds — bundle CONSTRAINTS); the projection never reads `config.json.bak-*`. **What the audit log may contain:** timestamps, seq, peer uid, verb, phase, plan_id, arg **names/ids** (skill id only after it passed the regex; pid), precondition values, outcome, `verified`/`connected`, verify lines (control-stripped + redacted), journal cursors. **No secrets in argv or env**: tasks inherit the worker's `process.env` and `/proc/*/cmdline` is world-readable until `ProtectProc=invisible` lands (safety §5.6); a `skill_id` reaches argv only after the `^[a-z0-9][a-z0-9._-]{0,63}$` check (§11); the TUI never prompts for keys/passwords (autopull constraint 1).

## Appendix B — the log grammar as regexes anchored at the timestamp

Pinned to daemon build `0.1.0+5bfa8261` (bundle §3.1; vps §3; fill6 §1). `TS` = `^(?P<ts>\d{4}-\d\d-\d\dT\d\d:\d\d:\d\d\.\d{3}Z) `. Phase lines keep the daemon's two-space indent. Compile with `re.ASCII`; match with `fullmatch` semantics (`$` anchored). **The redactor's control-character step (§13) runs before matching**, so a line carrying an escape sequence inside a `working:` message still matches `PHASE` on its stripped form and is never a different `kind` because of injected bytes. Anything that matches no pattern is `kind = unknown` and goes to LOG only.

```python
HEARTBEAT = TS + r"(?P<state>alive|disconnected) (?P<uptime>\d+m|\d+h\d+m|\d+d\d+h) · " \
            r"(?P<work>idle|(?P<running>\d+) tasks? running) · (?P<submitted>\d+) submitted" \
            r"(?: · fleet (?P<online>\d+) online, (?P<enrolled>\d+) enrolled)?" \
            r"(?: · (?:paused until (?P<until>\d\d:\d\d) after (?P<failed>\d+) failed runs?(?:: (?P<reason>.*?))? — run imd doctor" \
            r"|(?P<unregistered>token not registered as an agent — run imd doctor)))?$"

ACCEPTED_CODE     = TS + r"accepted (?P<role>implement|tests|review|integrate) (?P<node8>[0-9a-f]{8}) — (?P<paths>.+?) \(max (?P<max_turns>\d+) turns\)$"
ACCEPTED_RESEARCH = TS + r"accepted question (?P<node8>[0-9a-f]{8})$"
ACCEPTED_FUZZ     = TS + r"accepted campaign (?P<node8>[0-9a-f]{8}) — (?P<harness>.+?) \((?P<runs>\d+) runs\)$"

PHASE        = TS + r"  (?P<phase>preparing|working|checking|bundling|uploading|repairing): (?P<msg>.{0,160})$"
MODEL_LINE   = TS + r"  working: running (?P<rt>claude|codex|acp)(?: on (?P<model>\S+))?$"
MODEL_REFUSE = TS + r"  working: (?P<rt>\w+) refused model (?P<model>\S+); running on its default model instead$"

SUBMITTED    = TS + r"submitted (?P<role>implement|tests|review|integrate) for (?P<node8>[0-9a-f]{8})$"
ANSWERED     = TS + r"answered (?P<node8>[0-9a-f]{8}) with (?P<citations>\d+) citation\(s\)$"

RUNTIMES     = TS + r"runtimes: (?P<list>.+?) \(using (?P<rt>\w+)(?:, as asked)?\)$"        # restart boundary
PROFILES     = TS + r"execution profiles: (?P<profiles>.+)$"
```
